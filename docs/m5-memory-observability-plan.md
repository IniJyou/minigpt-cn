## 资源读数究竟缺了什么

冻结调用路径为FitBackend → ReplayBackend → RevisionBackend → LoraBackend。`m5_lora_run.py:379`的memory先调用CUDA synchronize，再顺序读取max_memory_allocated和max_memory_reserved；`m5_train_fit_run.py:456`补入设备总量，ResourceGuard在第250行起判断。

| 判断 | 冻结表达式 | 本次能否判定 |
| --- | --- | --- |
| 设备总量变化 | observed总量与guard建立时总量不等；字段缺省时沿用建立值 | 不能 |
| 峰值关系非法 | 不满足0 ≤ peak_allocated ≤ peak_reserved | 不能 |
| reserved余量不足 | peak_reserved > 建立时总量 − 1GiB | 不能 |

三项共用同一MemoryError，且采用短路判断；异常记录没有observed或各条件的结果。现有终端栈确认本次走到该MemoryError，而非synchronize本身抛错，但仍无法恢复任何触发时的数值。

建立时总量8,585,216,000 bytes，保留余量1,073,741,824，reserved上限7,511,474,176。已完成六步日志中的最大allocated/reserved分别4,435,415,040 / 5,110,759,424 bytes；这些是失败前保存的峰值，不能代替失败现场读数。

峰值在继承的Qwen加载入口、基座加载前reset一次；本续行路径不在恢复后、每组或每条样本后重置。因此它们覆盖加载、恢复及已执行计算，不能标为“当前样本独占显存”或“当前实时占用”。两项峰值也不是同一瞬间的活跃分配快照。allocator碎片、缓存、WSL/驱动记账等解释均待验证；本轮不认定CUDA OOM或具体硬件/库缺陷。

## 最小补充内容

另建观测入口及测试，不修改旧入口、runtime、协议、失败目录或检查点。新入口复用冻结的模型构造、完整状态恢复、样本布局、学习率、loss与梯度处理，只在控制流中明确观测上下文；不全局替换旧函数。新代码、定义、原文件摘要及CPU证据必须另行绑定后才可形成运行配置。

第一版只保存**原guard实际使用的那一份返回值**。保持原有同步及检查位置，不增加CUDA同步、额外allocator查询、峰值reset或empty_cache；不在异常处理里重新查询内存。这样先解决“哪一条门槛、什么数值、发生在哪里”的缺口，不能承诺一次定位碎片等深层原因。

每次原guard进入时先持久化enter事件；原采样返回后，在CPU保存不可变副本，计算并记录全部三个条件的布尔结果，再作与原逻辑相同的通过/停止决定。允许多项同时成立，不只报告短路遇到的第一项。时间上限仍是1800秒，`elapsed >= 1800`即停止；reserved等于上限可以通过。缺省总量的原有语义也须保留，记录字段缺失，不用新规则悄悄替代。

| 事件字段 | 用途 |
| --- | --- |
| event_id、UTC、monotonic_ns、guard elapsed | 关联进入/完成与墙钟边界；单调时钟负责耗时 |
| phase、stage、absolute step/microbatch、组内位置、sample_id | 区分组开始、collate前、反向及删除后、更新后、日志前重复检查 |
| input/target/sequence tokens、整组监督分母 | 确认实际布局及归一化，不保存正文或完整张量 |
| optimizer进入/返回、scheduler返回、最后完成更新 | 区分更新前失败、更新调用内部失败、更新后但日志前失败 |
| device、synchronize及读取状态、observed三项、预期总量和阈值 | 记录用于判定的原值；不把缺读数填成0 |
| 三项判定结果、异常类型/消息/traceback | 保留具体原因与复合失败，采样未完成时为unknown |

前向尝试账本继续在forward前flush+fsync。guard enter/result及optimizer/scheduler进入/返回标记也应在下一次模型操作前持久化，保证不从“最后一条训练日志”猜测更新数。若optimizer调用内部异常，只有进入标记而无返回时，更新状态记unknown，不能断言未改权重；CPU阶段要覆盖此分支。

synchronize或读数获取抛错时，保留原异常、已完成的读取阶段及最后成功事件ID；上次值只能标为历史值。日志写入/fsync失败立即停止，通过stderr尽力报告原异常和写入异常，不能把记录失败写成成功，也不能为补日志再运行模型。异常证据在清理前保存；清理后的读数不用于解释故障。观测I/O会增加耗时，时序不能保证与旧运行完全一致，墙钟门槛不因此放宽。
